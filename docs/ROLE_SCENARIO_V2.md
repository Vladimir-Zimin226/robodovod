# Объектный расчёт по ролям: склад, аэропорт, клиника

Состояние кода на 19.10.2026. Основной ввод: выбор объекта → роли → работы каждой роли → робот → покупка и аренда → результат. Старый процессный маршрут и его снимки остаются самостоятельными. Складские снимки `warehouse-role-analysis-v1` читаются как были сохранены; новые поля применяются только при новом preview/save. Аэропорт и клиника сохраняются под отдельными ключами `object_role_scenarios_v2_airport` и `object_role_scenarios_v2_clinic` в профиле проекта.

## Охват и источник

Источник типовых строк — `data/role-work/build_role_process_assumptions.py`. Он генерирует CSV, `frontend/src/roleWorkScenarioData.json` и [таблицу покрытия 35 пар](../data/role-work/role-coverage-v2.csv). В таблице результат поиска модели обозначен `DISCOVERY_RUNTIME_FUNCTION_MATCH`: точное число кандидатов зависит от активного каталога проекта и определяется при расчёте; статическая таблица не выдаёт непроверенную модель за найденную. В сценарии 35 пар: склад 8/8, аэропорт 13/13, клиника 14/14; уникальных ролей соответственно 8, 11 и 10. Статусы исходного C11 не менялись: 20 расчётных, 12 `REFERENCE_ONLY`, 3 `SAFETY_BLOCKED`. Для 12 справочных строк в генераторе названы отдельные технические подзадачи и остаточные ручные действия. Числа нового движка маркируются `ASSUMPTION_V2`; `USER_CYCLE` не назван паспортной формулой C11.

У аэропортового оператора тележек один штат 80 человек распределён 0,4+0,4+0,2; у санитаров клиники штат 40 распределён 0,5+0,3+0,2; у транспортировщиков штат 25 распределён 0,6+0,32+0,08. API отвергает сумму долей выше 1, чужую единицу, изменение статуса безопасности и подмену ссылки на исходную строку. Работы можно включать по одной. Парк суммируется по назначениям; совместное использование без расписания не предполагается.

Типовой поток работы = штат роли × доля работы × ручная выработка за смену. Редактируемый спрос задаётся в физической единице самой строки (`item`, `kg`, `delivery`, `m2` и др.). Выработка робота в шаблоне = ручная выработка за смену / часов в смене. Это **сценарная оценка**, не характеристика модели. Парк = `ceil(роботизируемый спрос / (выработка робота/час × часы/смену × смены/сутки × доступность) × (1 + резерв))`. Условные ставки до коэффициента = `min(штат роли × доля работы, роботизируемый спрос / ручная выработка за смену)`. Их сумма по работам роли не может превысить исходный штат.

Коэффициент ФОТ на каждой роли по умолчанию 0,5: потенциальные ставки × коэффициент × месячные расходы работодателя × 12. При 0 деньги не экономятся, при 1 учитывается полный потенциал; парк неизменен. Карточка показывает ФОТ и NPV при 0 / 0,5 / 1. Годовая база без роботов показывает полный ФОТ уникальных выбранных ролей; его не нужно суммировать с C11/C18 по тому же труду.

## Экономика и допущения

Цена покупки 3 млн ₽/робот и тариф RaaS 120 тыс. ₽/робот в месяц для 35 строк — **редактируемые бюджетные оценки без предложения поставщика**. Для складского старого маршрута цена из опубликованного каталога имеет приоритет; если её нет, используется отдельно помеченная сценарная цена из строки. Пользователь может снять предположение о цене или тарифе: соответствующая ветка становится частичной, другая рассчитывается самостоятельно. Для аренды складской формы общий сценарный тариф по умолчанию 150 тыс. ₽/робот в месяц; его можно заменить для конкретной модели.

Покупка: `CAPEX = парк × цена × (1 + доля внедрения)`, ежегодный сервис = `парк × цена × доля сервиса`, годовой эффект = экономия ФОТ − сервис, `TCO = CAPEX + сервис × горизонт`, `NPV = Σ(годовой эффект / (1 + ставка)^год) − CAPEX`, `ROI = (годовой эффект × горизонт − CAPEX) / CAPEX × 100%`. Срок окупаемости считается только при положительном годовом эффекте. Аренда: `CAPEX заказчика = парк × разовые вложения`, годовые расходы = `12 × парк × тариф + парк × дополнительные расходы заказчика`, TCO и NPV считаются аналогично. При нулевом CAPEX ROI на CAPEX = `N/A`; положительный NPV не превращает его в процент.

В тарифе RaaS по умолчанию предполагается сервис поставщика; обязанности, расходники, зарядка, площадка и гарантии требуют проверки. Общие расходы заказчика редактируются отдельно. Штатный шаблон использует `EMPLOYER_COST`: исходная gross ставка умножена в генераторе на сценарный коэффициент 1,302. Пользователь может выбрать `GROSS`; тогда указанная им начисленная ставка умножается на редактируемый общий коэффициент один раз. График, годовые дни, резерв, доступность, внедрение, сервис, ставка дисконта и горизонт видны и сохраняются. Эти оценки не подтверждают налоговую ставку конкретного работодателя.

## Подбор и безопасность

Кандидаты читаются из активного опубликованного discovery каталога и предварительно сопоставляются по функции в имени/описании. Текстовое совпадение не подтверждает грузоподъёмность, маршрут, санитарный режим, зрелость или доступность закупки. Для `clinic_waste_b` и `airport_apron_cleaning` фильтр требует соответствующего профильного описания; при отсутствии кандидата выбирается явно подписанный **сценарный тип без каталожной модели**, а не вымышленная модель. Цена и выработка остаются отдельными допущениями даже при выборе реального кандидата. Пилот/RND указан в списке моделей.

Три safety-строки можно выбрать и пересчитать. Базовый итог исключает их. Общий условный итог включает их только при включённом переключателе и показывает предупреждение. Для перрона остаются неподтверждёнными допуск, погода, зоны движения, модель и маршрут. Для отходов класса Б — санитарный режим, герметичность, маршрут, дезинфекция и пригодность модели. Число не означает разрешения на эксплуатацию.

## Проверка и выпуск

Адресные backend тесты: `backend/test_object_roles.py` и `backend/test_warehouse_roles.py` проверяют 35 числовых типовых строк, обе ветки, распределение людей, безопасность, единицы, неизвестную цену, коэффициент, сохранение, повторное открытие и optimistic locking. Frontend: `npm.cmd test` и `npm.cmd run build`. Локальный headless Chrome проверил две складские роли, 13 строк аэропорта и 14 клиники, обе денежные ветки и повторное открытие аэропорта с тестовым каталогом/ответами API. Это не production smoke и не проверка реального предложения поставщика.
