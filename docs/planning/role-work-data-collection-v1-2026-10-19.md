## Что собрать для каждого нового расчёта

Таблица сценарных значений: [`role-process-measurement-template-v1.csv`](../../data/role-work/role-process-measurement-template-v1.csv), UTF-8, разделитель `;`. Теперь она содержит **все 35 пар «процесс–роль»** из каталога C03. Числа получены из проверенных ячеек файла организаторов и явно описанных авторских допущений. Это не данные заказчика и не результаты замера. `measurement_date` оставлено пустым. Исходный файл организаторов не менялся. Чтобы одна таблица служила и для проверки, и для интерфейса, скрипт [`build_role_process_assumptions.py`](../../data/role-work/build_role_process_assumptions.py) генерирует CSV и [`roleWorkScenarioData.json`](../../frontend/src/roleWorkScenarioData.json); тест сверяет их построчно.

Поле `calculation_status` показывает границу применимости каждой строки:

| Статус | Строк | Применение |
| --- | ---: | --- |
| `CALCULABLE` | 13 | В C11 есть формула мощности, роль закреплена за одним процессом. Профиль можно предложить в форме после совпадения роли и численности. Для результата всё равно нужны корректные входы процесса и сохранённый C11. |
| `ALLOCATION_REQUIRED` | 7 | Сотрудники одной роли участвуют в нескольких процессах. Поле `process_allocation_fraction` обязательно для их подтверждённого профиля и теперь передаётся в C14; автоматическая подстановка доступна при совпадении полного штата роли. Общий расчёт проекта проверяет сумму долей по включённым процессам. |
| `REFERENCE_ONLY` | 12 | В C11 для операции нет формулы парка. Сценарные числа описывают работу, но денежный эффект этой строки сервис сейчас не рассчитывает. |
| `SAFETY_BLOCKED` | 3 | Для перрона либо отходов класса Б допуск робота и условия безопасности не подтверждены; заменяемая доля принята равной нулю. |

`confirmed=true` стоит у 13 строк `CALCULABLE` и 7 строк `ALLOCATION_REQUIRED`: владелец разрешил использовать эти числа как сценарные допущения. У остальных `confirmed=false` означает ограничение расчётного контура, а не отсутствие заполненной оценки. В каждой строке есть источник численности и ставки, единица выработки, минуты, доля, остаточная работа и ссылка `evidence_ref`. Поле `work_data_source=ASSUMPTION` у всех 35 строк.

Для склада оценочная начисленная ставка грузчика 80 000 ₽/мес. выбрана ниже ставки оператора погрузчика 120 000 ₽/мес. из таблицы; это **не рыночная статистика**. Месячные расходы работодателя во всех сценарных строках равны начисленной сумме × 1,302 — коэффициенту, который сам датасет задаёт в ячейках `Склад!C32`, `Аэропорт!C35`, `Медучреждение!C54`. Это сценарная конверсия, а не актуальный налоговый расчёт. У типового склада расходы грузчика составляют 104 160 ₽/мес. Там, где начисленная ставка отсутствует, она также оценена и помечена в `salary_source_ref`. Минуты в таблице условные: 600 минут из 11 часов на складе и 420 минут из 8 часов в остальных объектах; остаток — перерывы и работа вне данного процесса. Это **не результаты хронометража**.

Проверка целостности штата: складские группы занимают 175 из 180 человек, включая разделение 100 комплектовщиков на 80 отборщиков и 20 сортировщиков как допущение. Наземные роли аэропорта делят ровно 320 сотрудников; терминальная группа использует 150 из 180, ещё 30 не назначены. Инспекторы ВПП и охрана заданы отдельными сценарными группами и не приписаны к этим 500 сотрудникам. В клинике группа 65 человек разделена на 40 санитаров и 25 транспортировщиков; их доли по маршрутам суммируются до 1 для каждой роли. Только 6 из 28 работников пищеблока отнесены к доставке; остальные не включены в экономию. В C11 для общей роли вводится полный штат объекта. C14 ограничивает штат и высвобождение долей конкретного процесса; при объединении проекта сумма долей проверяется до расчёта.

Проверка единиц сделана для каждой строки: паллеты, строки отбора, м², штуки, порции, заявки/рейсы или килограммы соответствуют типу процесса. Переводы единиц помечены допущениями: например, 85 контейнеров отходов аэропорта × 25 кг/контейнер и 45 рейсов расходников клиники × 10 предметов/рейс. Для сценарных потоков без исходной цифры это указано прямо в `work_basis`. Дневной объём делится на число занятых в процессе сотрудников, учитывая, что каждый выходит в одну из смен суток. На шаге «Работа» отдельная кнопка заполняет пустой штат и расходы поддержанного процесса, в том числе общей роли; на шаге «Деньги» профиль предлагается лишь при совпадении **полной** численности роли в сохранённом C11. Источник остаётся `ASSUMPTION`. Изменение поля снимает подтверждение. Положительная экономия не означает гарантированное сокращение штата.

1. `object_role_headcount` — штат роли по расписанию. Если роль участвует в нескольких процессах, задайте `process_allocation_fraction` для каждого процесса на основе времени или графика; сумма долей одной роли не должна превышать 1. Одного человека нельзя посчитать как полностью высвобожденного дважды.
2. `monthly_amount_rub_per_person` и `monthly_amount_basis` — сумма за месяц на человека и её база (`GROSS` либо `EMPLOYER_COST`). Приложение использует расходы работодателя после выбора базы; не смешивайте две базы для одной роли. Приложите ведомость/оценку в `salary_source_ref`.
3. `manual_units_per_person_shift` и `manual_unit` — выполненные единицы **именно этого процесса** одним сотрудником за смену. Единица должна соответствовать C11: например, паллеты/смену для паллетного процесса. Строки заказа/час требуют явного перехода к строкам/смену и проверки соответствия `PICK`; их нельзя применить к паллетам.
4. `robotizable_task_minutes_per_person_shift` и `paid_process_minutes_per_person_shift` — наблюдаемое время заменяемых задач и всё оплачиваемое время роли в этом процессе. `robotizable_fraction = robotizable_task_minutes / paid_process_minutes`, от 0 до 1. В числителе учитывайте только задачи, которые действительно исчезнут при данном роботе; ручную приёмку, проверку, загрузку и исключения перечислите в `residual_operations`.
5. `work_data_source` — `USER` для данных объекта или замера, `ASSUMPTION` для сценарной оценки. В `work_basis` укажите период, способ замера, документ либо причину допущения; `measurement_date` и `evidence_ref` позволяют проверить исходные сведения. `confirmed=true` означает, что именно эти данные приняты для **нового** расчёта.

Если замера нет, для дополнительной роли допустимо явно подтверждённое сценарное допущение `robotizable_fraction=0`: положительной экономии этой роли пока нет. Для типового склада вместо нуля теперь принято обоснованное, но непроверенное на объекте значение грузчика `150/600 = 0.25`; его следует заменить после замера.

## Как данные попадают в сервис

- На шаге «Работа» вводятся роль, численность и месячная сумма. Сервис сохраняет их с техническим снимком C11. Если они неверны, требуется новый C11.
- На шаге «Деньги» для каждой роли вводятся доля, выработка, остаточные операции, тип источника и основание. Нажатие кнопки сценарных допущений принимает подходящие профили как допущения; при ручном вводе профиль подтверждается отдельно. Для основной роли значения доли и выработки связаны с существующими полями формы. Изменение значений снимает подтверждение.
- Отсутствующие или неподтверждённые данные дают частичный денежный результат и перечень нужных полей. Типовой файл и тестовые цифры не превращаются в подтверждённые факты объекта автоматически.

При переносе на сервер потребуется выпустить обновлённые backend и frontend и создать новый расчёт. Этот файл сам по себе не меняет исторические расчёты или production. Передача `process_allocation_fraction` в C14 и проверка общего штата по нескольким сохранённым процессам реализованы локально. Для `REFERENCE_ONLY` нужна соответствующая формула мощности C11; для `SAFETY_BLOCKED` — подтверждённые ограничения объекта и пригодность модели.
