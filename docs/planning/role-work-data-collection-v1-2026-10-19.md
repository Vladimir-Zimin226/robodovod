## Что собрать для каждого нового расчёта

Таблица сценарных значений: [`role-process-measurement-template-v1.csv`](../../data/role-work/role-process-measurement-template-v1.csv), UTF-8, разделитель `;`. Одна строка соответствует паре `process_id` + `role_id` из типового C03/C11. Пустое поле означает «неизвестно», а `0` — осознанное числовое утверждение. Все четыре строки заполнены **допущениями**, кроме явно указанных исходных чисел организаторов. `confirmed=true` означает принятое владельцем сценарное значение от 19.10.2026, а **не проведённый замер**. `measurement_date` пусто именно потому, что замера не было. CSV служит проверяемой таблицей; значения для кнопки типового объекта продублированы в [`roleWorkScenarioAssumptions.js`](../../frontend/src/roleWorkScenarioAssumptions.js), поскольку прямая загрузка CSV в браузер не реализована. Сверка двух представлений проверяется тестом.

Для склада оценочная начисленная ставка грузчика 80 000 ₽/мес. выбрана ниже ставки оператора погрузчика 120 000 ₽/мес. из таблицы; это **не рыночная статистика**. Месячные расходы работодателя во всех сценарных строках равны начисленной сумме × 1,302 согласно принятому в прежнем сценарии множителю, а не актуальному налоговому расчёту. У типового склада расходы грузчика составляют 104 160 ₽/мес. Для аэропорта и клиники начисленные ставки взяты из ячеек организаторов, но число сотрудников в конкретной операции, выработка и доля остаются допущениями. Минуты в таблице условные: оплачиваемые 600 минут из 11 часов на складе и 420 минут из 8 часов в остальных объектах; остаток — перерывы и работа вне данного процесса. Это **не результаты хронометража**.

Проверка единиц: склад — паллеты, аэропорт — м², клиника — порции. Дневной объём делится на всех сотрудников данной роли, учитывая, что каждый выходит в одну из смен суток. Строки не применяются к другим объектам без оценки их штата и нагрузки. На шаге «Работа» кнопка типового объекта подставляет соответствующий штат и суммы; на шаге «Деньги» кнопка допущений подставляет долю и выработку всех присутствующих ролей. Источник каждого профиля остаётся `ASSUMPTION`. Изменение поля снимает его подтверждение. Эти значения создают воспроизводимый **сценарный**, а не измеренный, денежный расчёт; положительная экономия не означает гарантированное сокращение штата.

1. `object_role_headcount` — штат роли по расписанию. Если роль участвует в нескольких процессах, задайте `process_allocation_fraction` для каждого процесса на основе времени или графика; сумма долей одной роли не должна превышать 1. Одного человека нельзя посчитать как полностью высвобожденного дважды.
2. `monthly_amount_rub_per_person` и `monthly_amount_basis` — сумма за месяц на человека и её база (`GROSS` либо `EMPLOYER_COST`). Приложение использует расходы работодателя после выбора базы; не смешивайте две базы для одной роли. Приложите ведомость/оценку в `salary_source_ref`.
3. `manual_units_per_person_shift` и `manual_unit` — выполненные единицы **именно этого процесса** одним сотрудником за смену. Единица должна соответствовать C11: например, паллеты/смену для паллетного процесса. Строки заказа/час требуют явного перехода к строкам/смену и проверки соответствия `PICK`; их нельзя применить к паллетам.
4. `robotizable_task_minutes_per_person_shift` и `paid_process_minutes_per_person_shift` — наблюдаемое время заменяемых задач и всё оплачиваемое время роли в этом процессе. `robotizable_fraction = robotizable_task_minutes / paid_process_minutes`, от 0 до 1. В числителе учитывайте только задачи, которые действительно исчезнут при данном роботе; ручную приёмку, проверку, загрузку и исключения перечислите в `residual_operations`.
5. `work_data_source` — `USER` для данных объекта или замера, `ASSUMPTION` для сценарной оценки. В `work_basis` укажите период, способ замера, документ либо причину допущения; `measurement_date` и `evidence_ref` позволяют проверить исходные сведения. `confirmed=true` означает, что именно эти данные приняты для **нового** расчёта.

Если замера нет, для дополнительной роли допустимо явно подтверждённое сценарное допущение `robotizable_fraction=0`: положительной экономии этой роли пока нет. Для типового склада вместо нуля теперь принято обоснованное, но непроверенное на объекте значение грузчика `150/600 = 0.25`; его следует заменить после замера.

## Как данные попадают в сервис

- На шаге «Работа» вводятся роль, численность и месячная сумма. Сервис сохраняет их с техническим снимком C11. Если они неверны, требуется новый C11.
- На шаге «Деньги» для каждой роли вводятся доля, выработка, остаточные операции, тип источника и основание; пользователь отдельно подтверждает профиль. Для основной роли значения доли и выработки связаны с существующими полями формы. Изменение значений снимает подтверждение.
- Отсутствующие или неподтверждённые данные дают частичный денежный результат и перечень нужных полей. Типовой файл и тестовые цифры не превращаются в подтверждённые факты объекта автоматически.

При переносе на сервер потребуется выпустить обновлённые backend и frontend и создать новый расчёт из типового объекта. Этот файл сам по себе не меняет исторические расчёты или production. Для человека, участвующего сразу в нескольких процессах, распределение общего штата между ними остаётся отдельной задачей: сценарные строки выше относятся к одному активному процессу на объект.
