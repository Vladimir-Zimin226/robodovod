# Проверка замечаний из «фиксы» (29.09.2026)

Статус: локальный аудит, план и выполненные проверяемые исправления.
Область: оба файла `fix.txt` и `Fix 2.txt` (пункта Fix 3 в них нет).
Начальное дерево: изменены `backend/economics_orchestrator.py`,
`docs/planning/README.md`; есть посторонние неотслеживаемые файлы. Их не менять.

## Иерархия источников и версии

Официальное ТЗ (`1. ФЦ БАС.pdf`, физическая стр. 7, §3.5) требует прозрачных
допущений, базового/покупного/RaaS сравнения и перечисленных метрик; отдельного
обязательного налогового режима в нём нет. Дополнения (физические стр. 1–2,
§2.1–2.4) задают собственные средства и разрешают команде выбрать состав
затрат, амортизацию и модель RaaS, раскрывая допущения. PDF прочитаны напрямую;
старые планы использованы для идентификации исполняемой политики, а не как
нормативные акты. Действующая методика — `calculation-policy-decisions-v1.md` (K08,
K12, K17, K27), C16 v1/v2, C17 v1, C18 v1 и registry v1. Reference v2 Жени
хранится как review backlog (`zhenya-reference-v2-delta.md`), а не автоматически
заменяет принятые решения. Золотые снимки v1/v2 служат доказательством
воспроизводимости, а не основанием менять исторические ответы.

Точные SHA-256 обоих замечаний, семи reference-файлов, двух официальных PDF,
registry и принятых политик: [manifest источников](evgeny-fixes-source-manifest-2026-09-29.json).
Он воспроизводится `scripts/audit_evgeny_fixes_sources.py`; SHA-256 registry
совпадает с `registry-v1.manifest.json`. Reference v2 — версия 3.2 от
18.09.2026, тогда как registry v1 привязан к прежним R02/R03 и отдельной policy.

| Fix 6: денежные веса FOT в C18 | Методическое решение | C18 v1 использует число людей для распределения представления; object FOT и project NPV корректны. Reference о ролевом ФОТ не устанавливает правило разнесения общего FOT по процессам. Один денежный вес базы для base/scenario не учитывает различия высвобождения по ролям; отдельно нужны правила общих операторов/техников и unallocated roles. При `finance_status=INCOMPLETE` C18 уже отклоняет запрос, поэтому предлагаемый fallback без зарплат не делает такой расчёт допустимым. | C18 v2: разные оклады и темпы высвобождения, missing salary, нулевой вес, перестановка процессов, сумма по копейкам и неизменный project NPV. |
| Fix 7: доход в RaaS | Уже исправлено | C17 включает `scenario-additional-income` в `scenario_non_robot`; исключает только purchase OPEX. При версии C16 v3 C17 получает индексированные строки без правки C17. | Сравнение C17 с включённым/исключённым доходом; ежегодная разность равна индексированной строке. |
| Fix 8: NPV в investor report | Подтверждено | C16/C17/C18 хранят три NPV, но сохранённая comparison projection для PDF теряет абсолютный scenario NPV. версионированного решения; приёмочные условия выше задают проверяемый объём.

## Выполненная реализация

- C16 `full-cashflows-reconciliation-v3` применяет к дополнительному доходу
  тот же registry `finance.inflation.other-opex`, что задаёт 5% в действующем
  снимке. Сумма согласована и в line ledger, и в EBITDA/CF/NPV. Выбор явный:
  `analyze_financials(request, engine_version="full-cashflows-reconciliation-v3")`.
  Default остаётся v2; приложение сейчас явно исключает дополнительный доход.
  Это отдельный доступный профиль, без миграции старых runs и registry.
- Новый fixture `financial-result-v3.additional-income.golden.json` и его
  отдельный генератор не перезаписывают v1/v2. C17 принимает v3 через binding
  результата comparator; расширены enum в обеих затронутых JSON schemas.
- `economics_final._project_metrics` сохраняет три готовые метрики C18
  в открытом для метрик контракте comparison. Финансовая арифметика не меняется.
  PDF `investor-presentation-v2` проверяет согласованность с базой и инкрементом;
  старые снимки и неполная экономика продолжают экспортироваться.

Доказательства воспроизведения, окончательные команды тестов и ограничения
окружения будут закреплены отдельным протоколом проверки.
