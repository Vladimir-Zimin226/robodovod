Статусы:

- **Реализовано** — есть действующий код и подтверждающие проверки; это не

- **Частично** — основа работает, но обнаружен конкретный разрыв требования

физические модели для всех операций аэропорта/клиники не являются
обязательным условием финала.

## 1. Замечания пользователя

### 1.1. Связана ли симуляция с расчётом

**Сохранённая симуляция связана с расчётом на сервере.**

- `backend/simulation_artifacts.py`: `owned_run()` допускает принадлежащий
  пользователю успешный `FULL_ANALYSIS`; `verify_run_binding()` проверяет
  проект, точное равенство ScenarioSpec и его digest. Сохранение/загрузка
  проверяют request/report digests и replay-привязки.
- `backend/simulation_api.py`: запуск по пути проекта/run отвергает чужой
  или несовместимый сценарий; артефакт сохраняется отдельно от immutable run.
- Все **4 из 4** артефактов бекапа ссылаются на существующие успешные
  `FULL_ANALYSIS`; их ScenarioSpec полностью совпадают со снимками runs, SHA сценария
  совпадают. Все четыре отчёта имеют verdict `CONSISTENT`.
- `frontend/src/components/TechnicalVisualization.jsx` создаёт связанный
  технический economics run от исходного C11; деньги для запуска не нужны.
- `backend/calculation/scheduling.py` использует сохранённые спрос, парк,
  номинальную/эффективную мощность, пакет и график; вычисляет очереди,
  выполненный поток, ожидание и отклонение. Это модель процесса, а не только
  анимация. Норматив производительности при этом является входом модели,
  а не независимо измеренным фактом об оборудовании.

**Открытые вопросы соответствия пп. 3.6.1–3.6.3:**

- В `CommercialScenariosV2.jsx` переключение вкладки покупки/услуги и
  неопределённости не меняет `buildEconomicsSimulationRequest()`:
  для run используется один ScenarioSpec, собранный от PURCHASE/BASE.
  Это допустимо для общих физических входов, но пользователь должен видеть,
  какой именно физический сценарий проигрывается. Финансовый ramp и техническое
  изменение нельзя выдавать за уже смоделированное переключение.
- Текущий селектор симуляции выбирает сохранённые технические варианты
  «паллетная перевозка / цепочка», а не все бизнес-сценарии.
- Зарядка учтена агрегированно; в базовой схеме написано «точка не задана».
  ТЗ требует показать точки операций и зарядки. Условную точку надо отличить
  от подтверждённого плана объекта; её положение не должно менять расчёт.
- В интерфейсе доступны данные симуляции JSON, но нет сохранения самой
  визуализации изображением. Старые четыре артефакта не подтверждают новый
  production-проход 220 паллет/сутки → 120 м → новая симуляция → повторное
  открытие → экспорт.

Вывод: **не переписывать симулятор с нуля**; завершить понятную привязку,
выбор и контроль параметров, визуальный экспорт и новую приёмку.

### 1.2. XLSX, страница шаблонов и интервью во внешней LLM

`backend/project_file_intake.py` уже принимает XLSX/CSV, проверяет типы,
единицы и диапазоны. Есть preview/apply и сохранение происхождения файла.
Однако генератор `build_csv_template()` и API
`/api/project-file-templates/{profile_code}.csv` выдают **только CSV**.

Текущий шаблон имеет поля `profile_code, parameter_code, value, unit` и
заполнен defaults профиля организаторов. XLSX-шаблона с инструкциями,
отдельной доступной гостю страницы и внешнего интервью-промпта нет.
`ProjectFileIntake` появляется только при выбранных проекте и BASE-сценарии.

Есть дополнительный разрыв: `IntakeScreen.jsx` переносит импорт в новый
расчётный маршрут автоматически только для складской перевозки. Нужные
новому пути batch и месячная gross-зарплата подтверждаются вручную; для
других процессов файл сохраняется с предложением перенести данные руками.
Нельзя просто сделать XLSX из старого CSV и объявить закрытым новый путь.

### 1.3. Экспорт по ТЗ

**Что существует:** отдельный читаемый PDF, PDF-preview и ZIP с CSV,
Snapshot.json, manifest и источниками. Экспорт строится из сохранённых
снимков, а не из изменённых полей на экране. Есть проверка владельца,
digests и предупреждение о предварительной оценке.

Пункт **3.7.3 допускает CSV вместо Excel**. Поэтому отсутствие `.xlsx`
само по себе не означает, что форматная часть ТЗ полностью провалена.
Но текущие CSV в архиве — главным образом технические строки
`path/value/source_ref/status`, а не удобные сравнительные расчётные таблицы.
PDF/ZIP не закрывают все требования к составу и удобству финального пакета.

**Подтверждённые пробелы:**

- нет прямой выгрузки XLSX-книги и понятной сравнительной CSV-таблицы;
- нет визуального экспорта SVG/PNG/страницы PDF с 2D и её KPI (3.7.4);
- нет единой основной таблицы «без роботов / покупка / услуга» со всеми
  обязательными метриками;
- ROI/TCO рассчитаны в C16/C17, но `_financial_projection()` и
  `_report_facts()` в `economics_orchestrator.py` не сохраняют их в публичной
  проекции нового основного результата. `financialView()` и новый читаемый
  PDF показывают NPV, потоки и payback, но не полный набор ROI/TCO.
  Наличие метрик на старом legacy dashboard этот разрыв не закрывает;
- отдельного опубликованного примера финального PDF + таблиц + визуализации
  для сдачи по 8.2.7 в изученном комплекте не найдено.

ROI покупки в ядре имеет базу CAPEX, а существующий показатель услуги — TCO.
Их нельзя без пояснения сравнивать под одной подписью «ROI». Показатели,
знаменатель и статусы N/A надо явно согласовать в новой проекции; экспорт
не должен вычислять недостающие деньги самостоятельно. Старые снимки
сохраняются, отсутствующие в них показатели так и обозначаются.

Чувствительность тоже требует завершения: production `_sensitivity()`
вызывается для **PURCHASE/BASE**, и её варианты повторно исполняют именно
PURCHASE/BASE. Один общий блок на экране не подтверждает чувствительность
каждого сценария по 3.5.6, особенно RaaS. Нужна явная привязка к сценарию
и минимум три релевантных параметра для каждого сравниваемого варианта.

### 1.4. Ручное управление и обновление каталога

**Требование 3.3.5 не выполнено.** В действующем `AdminUsersScreen` и
`/api/admin/*` есть пользователи и диагностический ZIP, а не редактор решений.
Ручного создания/редактирования модели, товарной позиции, предложения,
ТТХ, источника и публикации каталога в админском интерфейсе нет.

**Как обновляется сейчас:**

1. Подготавливается и проверяется версионированный bundle в `data/import/`.
2. Серверный инструмент `catalog-import` исполняет BASE/ENRICHMENT,
   сначала VALIDATE_ONLY, затем COMMIT.
3. `catalog-activation` валидирует и публикует версию; отдельно переключает
   discovery и capacity slots, для capacity нужен approval report.
4. Backend читает активный опубликованный snapshot через CatalogRuntime.

Это инженерный CLI-процесс, описанный в `PRODUCTION_DEPLOYMENT.md`, а не
ручное управление через веб-интерфейс по ТЗ. Планового автоматического
обновления нет; оно является преимуществом, не обязательным условием.
В свежем бекапе одна опубликованная версия `organizer-catalog-v4`, две
активации и пять import runs; таблицы description imports/enrichments пусты.
Наличие инструментов description enrichment не доказывает их применение
к этому production-каталогу.

Будущий редактор должен создавать новые версии и не менять опубликованные
снимки или runs. Добавление описания в discovery не равно разрешению
использовать модель для расчёта: данные и поддержанный физический профиль
проходят отдельные проверки.

### 1.5. Фильтрация и подбор

Поиск, сортировка и сравнение действительно есть. `CatalogScreen.jsx`,
`catalogPresentation.js` и `/api/catalog/models` поддерживают семейство,
тип, производителя, участие в расчёте и текстовый поиск. Сравнение выбирает
2–3 конкретные позиции; дубли моделей с разными предложениями сохраняются.

**Недостаточно для полного 3.3.1/3.4:**

- hierarchy API содержит семейство → тип, а не отрасль → объект → процесс
  → тип → продукт;
- `objectType` на странице используется в подписи, но не передаётся в
  `filterAndSortCatalog()`. Выбор склада/аэропорта/клиники не фильтрует каталог;
- нет отдельных фильтров процесса, отрасли, доступности, диапазонов
  грузоподъёмности/габаритов/прохода/цены и качества данных;
- C05 и объяснимое сравнение кандидатов существуют, но ограничения массы,
  прохода и интеграций заполняются позднее в отдельной панели. Полный контекст
  объекта не объединён с исходной подборкой;
- ручная форма через `demoCandidates()` оставляет только три авторских
  профиля. Brain через `brainCandidates()` использует более широкий совместимый
  пул. Из бекапа: 21 расчётная модель из 187, включая 15 со статусом
  WITH_ASSUMPTIONS; 143 имеют неподдержанный физический профиль. Эти статусы
  нельзя заменить одним флагом «подходит»;
- ручное добавление в сравнение разрешено в информационном каталоге, но
  надо проверить сохранение предупреждений, когда позиция исключена
  автоматическим подбором или принадлежит другому классу.

### 1.6. Иконка браузера

`frontend/index.html` подключает `public/favicon.svg`. Это прежний фиолетовый
графический знак, не RD; отдельного ICO/PNG fallback нет. Запрос пользователя
на читаемую иконку **RD** включён в план. Само ТЗ не требует конкретного знака.

## 2. Скорость ИИ по свежему бекапу

| Запрос | Наблюдение |
|---|---|
| Brain `/turn` | 5 событий HTTP 200: 11,849; 13,427; 24,839; 20,414; 60,065 с |
| Brain | Медиана 20,414 с; максимум близок к установленному timeout 60 с |
| Roboexpert `/summary` | 1 событие HTTP 200, 14,904 с |
| Остальные запросы | 11 событий, 5–328 мс |

Это маленькая выборка, не нагрузочный тест. Последняя сохранённая версия
Brain содержит `model_error`. `/turn` возвращает HTTP 200 и при fallback,
поэтому статус HTTP не доказывает успешный ответ модели. Совпадение 60,065 с
с timeout и ошибкой профиля согласуется с ожиданием внешнего API, но в
бекапе нет отдельных фаз запроса/ответа провайдера для точного разложения.

Код синхронно ждёт Yandex API, non-streaming; браузер всё это время находится
в общем busy-состоянии. У DeepSeek выходной лимит расходуется также до
появления конечного JSON: в проверках исправления небольшой Brain-диалог
использовал 2196 completion tokens и около 32 с. Лимиты 900/450 были слишком
низкими; их возвращение не является корректной оптимизацией.

Следующая работа: измерить latency провайдера отдельно, явно показывать
статус/таймаут/fallback, сократить контекст и необязательные обращения,
проверить поддержанные настройки генерации на синтетических диалогах.
Основная модель остаётся DeepSeek V4 Flash. Экономический расчёт отделён от
LLM: его целевой предел по ТЗ — 10 с, ожидание LLM не надо считать временем
работы финансового ядра.

## Вывод

Основной складской расчётный путь и защищённое хранение доказательств есть.
Утверждение «все обязательные пункты ТЗ закрыты» сейчас неверно. Главные
разрывы: веб-редактор каталога/нормативов, контекстная подборка, целостный
file → новый расчёт маршрут, общая таблица обязательных финансовых метрик,
удобные расчётные экспорты и экспорт визуализации. ИИ уже доступен, но его
ожидание и fallback требуют отдельного завершения UX/диагностики.
