# Доработка сервиса после первого живого запуска — 24.09.2026

## Цель и исходное состояние

Сделать опубликованный «Рободовод» понятным руководителю склада или производства: каталог с изображениями, читаемый отчёт, наглядная работа роботов, помощник по выбору решения, объяснимые неполные входные данные и понятный архив доказательств.

План выполняется **по этапам 1–7**. После каждого этапа — только проверка затронутого поведения и отдельный коммит. Полный набор проверок и выпуск — на этапе 8. Не подменять неизвестные данные нулём, подтверждённой ценой или положительным техническим вердиктом. Сохранённые `analysis_runs` и `simulation_artifacts` не переписывать.

Подтверждено текущими материалами:

- Локальный `main` чист, `HEAD=c89a660f6ee70cb380b05b1fc182e757d0248f7b`. В присланном выводе SSH на этом коммите успешно пересозданы и стали healthy `backend`, `frontend`, `caddy`; БД уже на миграции `0011_simulation_artifacts`. Отдельного подтверждения полного пользовательского сценария на HTTPS пока нет.
- `backup/` — **диагностический снимок**, а не восстановительный дамп: 30 файлов, около 5,8 МБ; все SHA-256 совпали с `manifest.json`. Снимок исключает пароли, сессии, загруженные файлы и байты Docker/Caddy логов. В нём 3 `analysis_runs`, 1 `simulation_artifact`, 223 строки каталога, но **0** `catalog_media_assets` и **0** `catalog_position_media`. Это объясняет пустые картинки в UI: `CatalogScreen.jsx` показывает заглушку, когда API не отдаёт `media.url`.
- Исходный официальный PDF находится локально в `Разобрать/Материалы от организаторов/Датасет/ФЦ БАС — Каталог внедрения 2008 1247.pdf` (84 906 007 байт). Уже есть `catalog-media` Compose service и детерминированный импорт 223 изображений в `backend/catalog_media.py`; нужно проверить доступность PDF и volume на сервере, импортировать и проверить API/браузер. Не рисовать вымышленные изображения вместо официальных.
- Отдельный PDF строится в `backend/calculation/readable_report.py` из immutable snapshot, но сейчас содержит `Run`, `revision`, `C05`, `gross`, `RaaS`, `NPV`, `NOT_AVAILABLE`, digest и другие коды без простого объяснения. И API, и браузер именуют файл `robomera-report-<run_id>.pdf`.
- 2D в `frontend/src/simulation2dModel.js` раскладывает зоны прямоугольниками и двигает роботов по условной петле; `RobCraft` имеет задачи, точки подбора/выгрузки и зональные маршруты. 2D уже честно отмечает условную геометрию, но не выглядит как вид сверху на склад с операциями.
- Навигация «Процесс» сейчас отправляет в `IntakeScreen`, где виден старый заголовок «РобоМера — AI-аудитор». Это также текущий вход в расчёт; при замене его необходимо оставить очевидный путь к рабочему расчёту.
- Полный C13–C21 сейчас требует все поля и подтверждения; `frontend/src/economicsInputV2.js` и backend отвергают пропуски. Нужна явная семантика неполного сценария, а не автоматические нули.
- ZIP содержит девять машинных CSV-разделов, `Snapshot.json`, `manifest.json` и технический `Report.pdf` с распечаткой снимка. Файлы и ограничения не объяснены обычному читателю.

## 1. Изображения библиотеки решений

**Работа.** Локально прогнать существующий `catalog-media` импорт на временной БД/volume с официальным PDF и подтвердить ровно 223 соответствия «позиция → страница/слот → SHA-256 → файл». Сверить структуру `media.url` в `/api/catalog/models` и `/api/catalog/positions/{id}` с тем, что читает `CatalogScreen`. На сервере проверить только наличие исходного PDF по пути Compose и подключённого `catalog_media` volume, затем выполнить существующий идемпотентный импорт для активной версии `organizer-catalog-v4`. Если PDF на сервере отсутствует, передать именно этот официальный файл и использовать `OFFICIAL_CATALOG_SOURCE_DIR`; без новых схем БД.

**Готово, когда:** API возвращает медиа для 223 позиций; несколько карточек из разных семейств и открытый диалог показывают изображения, HTTP media отдаёт 200 и ожидаемый MIME, повторный импорт не создаёт дублей, чужой/несуществующий SHA даёт 404. Любые непокрытые позиции остаются с честной заглушкой и известной причиной. Проверить в браузере загрузку после перезагрузки и ошибку при недоступном файле. Отдельный коммит — только если потребуется кодовое исправление; сам импорт зафиксировать в рабочем журнале этапа.

## 2. Отчёт для русскоязычного читателя и название файла

**Работа.** Сделать новую версию генератора отчёта и ясный макет в цветах приложения: обложка с «Рободовод», номером полного run ID и датой расчёта; затем «Какой процесс оцениваем», «Сейчас», «После покупки роботов», «При аренде роботов (RaaS)», «Сравнение денег по годам», «Что известно и что ещё подтвердить», «Источники и методика». На первом развороте показать исходный объём работ, сотрудников/затраты и сроки; для покупки — парк, объём после внедрения, CAPEX/OPEX, годовой эффект и NPV; для RaaS — тариф, включённые услуги по введённым условиям, годовой эффект и NPV. Каждый показатель брать из сохранённых входов/результатов либо из связанного сохранённого C11 run с проверенным digest и тем же владельцем. При отсутствии исходного значения писать «нет данных для оценки» и причину; не пересчитывать экономику в PDF и не подставлять фактическую производительность из 3D. Исторический C16 v1 помечать как расчёт с известной ошибкой. Сохранить поиск по русскому тексту и корректные переносы, рубли, даты, единицы, числовой формат.

В UI и `Content-Disposition` дать имя вида `Рободовод, отчёт № <run-id> от <ДД.ММ.ГГГГ>.pdf`, с ASCII fallback и корректным UTF-8 `filename*` для браузеров. В тексте использовать русские пояснения вместо внутренних кодов; технические digest/версии оставить в приложении к отчёту.

**Готово, когда:** PDF читается глазами как отдельный документ, отражает фактический baseline и обе модели приобретения без ложных данных, открывается в обычном PDF-просмотрщике, текст выделяется/ищется, имя корректно в Chrome/Windows, повторное скачивание того же run воспроизводит те же значения. Проверить кейсы полного, частичного и старого C16 v1 run; отдельный коммит.

## 3. 2D как упрощённый вид склада сверху

**Работа.** Из `ScenarioSpec` и согласованного с `RobCraft` описания задач построить схематичный план склада сверху: рабочие зоны, стеллажные проходы, точки приёмки/отгрузки, место ожидания/зарядки, маршрут робота, конкретные точки подбора и выгрузки. Каждый робот принадлежит своей зоне и получает задания этой зоны; на экране видны этапы «едет за грузом → погрузка → везёт груз → выгрузка → возврат/ожидание», а груз меняет состояние. Несколько роботов/зон не накладываются друг на друга. Управление стартом, паузой, скоростью и replay остаётся детерминированным; при reopen тот же seed и сценарий дают те же видимые события. Взять общие идентификаторы зон/задач/точек и единый адаптер сцены для 2D/3D там, где это реально поддерживается. Не выдавать синтетическую карту за загруженный план здания; при геометрии `PROVIDED` показывать фактически имеющиеся координаты только если они доступны, иначе явную пометку «расположение условное». C23 остаётся источником KPI, а не нарисованная анимация.

**Готово, когда:** в складском golden path робот видимо забирает и выгружает паллеты в обозначенных точках своей зоны; 2D и RobCraft называют одинаковые зоны и задачи; смена зоны и reopen сохраняют привязку; отсутствие геометрии/задач объясняется на экране. Проверить выборочные кадры и автоматические тесты состояния/маршрута; отдельный коммит.

Рабочий intake и результаты должны оставаться доступны напрямую через отдельный ясный пункт «Расчёт». Убрать «РобоМера» из пользовательского заголовка и видимого текста этой области; проверить ссылки, сохранённый проект, обратную навигацию и мобильное меню.

**Готово, когда:** новый пользователь не попадает в legacy-экран по пункту «Процесс» и может без препятствий пройти существующий расчёт; отдельный коммит. Заглушка сменится помощником на следующем этапе.

## 5. Помощник: каталог, сравнение и поиск в интернете

**Работа.** Использовать серверные `YC_API_KEY`/`YC_FOLDER_ID`, которые уже предусмотрены в Compose, без вывода или копирования секретов в репозиторий. При старте этапа проверить доступные права/квоты по официальной документации. Подготовить версионированный поисковый корпус из **активной** версии каталога: карточка позиции, подтверждённые характеристики, назначение, ограничения, страница официального PDF, дата/источник, участие в capacity-расчёте. Индекс обновлять при смене активной версии; не смешивать черновые enrichment/неподтверждённые цены с официальными фактами. Начать с поиска по версии каталога и цитирования карточек; затем добавить разговорный сбор потребностей и сравнение 2–3 вариантов в таблице с одинаковыми критериями. Для «найти в интернете» — отдельное явное действие/режим с источниками, датой поиска и отличием веб-сведений от каталожных; внешняя страница не меняет проверенный каталог, eligibility или цену. Ответ может предложить черновик параметров проекта, но только пользователь подтверждает их перед расчётом. LLM не вычисляет fleet/NPV и не пишет напрямую в сохранённый run.

Документация Yandex Cloud описывает [Vector Stores](https://yandex.cloud/en/docs/ai-studio/vectorStores/) для поиска по собственным данным и [Yandex Search API](https://yandex.cloud/ru/services/search-api) для поиска в интернете; конкретную комбинацию API, доступы и стоимость проверить при реализации. Предусмотреть ограничение запросов и размера контекста, защиту от инструкций в найденных страницах, tenant isolation, отсутствие секретов в ответе, понятное поведение при недоступности Yandex. Если храним переписку — только в границах пользователя/проекта; для первой версии можно обойтись без новой таблицы.

**Готово, когда:** помощник уточняет задачу, ссылается на конкретные карточки и страницы, сравнивает реальные позиции, явно отделяет внешний поиск, не обещает закупку и не превращает C05 `NEEDS_VALIDATION` в `PASS`. Проверить запросы без ответа в каталоге, спорные характеристики, отказ Yandex, злонамеренную веб-страницу, чужой проект и диалог до черновика intake; отдельный коммит.

## 6. Неполные данные без сломанного расчёта

**Работа.** Сначала составить матрицу входных полей C03/C11/C13–C21: обязательное для технической допустимости, обязательное только для одной финансовой ветки, допускающее `UNKNOWN`, допускающее честный пользовательский диапазон/допущение. Переделать форму: простое название, единица, объяснение «зачем нужно», пример, источник, подсказка для нуля и пустого поля; показывать ошибки рядом с полем и список того, что ещё требуется для конкретного результата. Backend должен возвращать структурированный частичный результат и причины пропуска показателя/сценария; не отвечать сырым 422/500 на ожидаемые пробелы. Считать доступные capacity/экономические ветки только при достаточных входах, неизвестные финансы обозначать `не рассчитано`, не менять неизвестный legacy `fte_cost` на gross и не выдавать сценарное допущение за подтверждение поставщика. Новую семантику версионировать, старые runs и golden оставить воспроизводимыми.

**Готово, когда:** пользователь может оставить допустимое поле пустым, сохранить/увидеть частичный результат и получить конкретный следующий шаг; существенный пропуск не рождает ложную сумму/NPV/рекомендацию. Проверить пустое/0/отрицательное/неверную единицу, отсутствие RaaS-тарифа и данные C05; отдельный коммит.

Положить туда же новый читаемый PDF отчёта или ясную ссылку/точное имя, а старый технический dump вывести из позиции главного документа. Объяснить `NOT_AVAILABLE`, пустые разделы, C23 evidence и различие «доказательство расчёта» / «подтверждение факта поставщика». **Готово, когда:** пользователь, открыв ZIP, сразу видит точку входа и может объяснить назначение каждого файла; пакет повторяем для того же run, браузер скачивает его, архив распаковывается в Windows, старый run не изменён. Отдельный коммит.

## 8. Полная проверка и выпуск

После последнего этапа один раз выполнить полный регрессионный набор: backend с PostgreSQL и миграцией на пустой БД, frontend/RobCraft тесты, lint/build, golden C11/C13–C23, исторический C16 v1 replay и новый v2, `tenant isolation`, CSRF и проверки экспортов. В реальном браузере пройти `каталог → помощник/расчёт → API → результат → 2D/3D → сохранение → reopen/replay → PDF/ZIP`; проверить имена файлов, изображения, русский текст, целостность архивов и видимый смысл статусов. Повторить на мобильной ширине. Публиковать только прошедший `main` отдельными коммитами обычным fast-forward, без force push; на сервере разворачивать именно проверенный HEAD. После запуска проверить `/ready`, состояние Compose, главную страницу, API каталога/медиа и пользовательский путь на HTTPS. Зафиксировать, какие бизнес-факты всё ещё не подтверждены. Серверные бекапы в этот план и команды выпуска **не включать**; новые миграции БД для этих этапов не запланированы.

### Простые команды выпуска из Windows CMD после зелёных проверок

Эти команды относятся **к концу этапа 8**, а не к сегодняшнему составлению плана. Из CMD:

```cmd
ssh robodovod
```

Затем в открывшейся Linux-сессии (после публикации проверенного `main`):

```sh
cd /opt/robodovod
git pull --ff-only origin main
sudo docker compose --env-file .env.production -f compose.yaml -f compose.production.yaml build backend frontend
sudo docker compose --env-file .env.production -f compose.yaml -f compose.production.yaml up -d --wait --no-deps --force-recreate backend frontend caddy
curl -fsS https://robodovod.ru/ready
```

Если к выпуску появится новая миграция, её необходимость и порядок запуска нужно описать по фактическому изменению; приведённые команды исходят из плана без новой миграции.
