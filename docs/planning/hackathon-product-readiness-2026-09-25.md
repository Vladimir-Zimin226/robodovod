## Целевой путь на защите

`лендинг → выбрать демо склада или свой процесс → ответить на короткие вопросы
→ сравнить 2–3 подходящих позиции с источниками → подтвердить поля и допущения
→ C11 + экономика доступных веток → 2D/C23 с KPI → сохранить → открыть снова
→ скачать PDF/ZIP`.

Склад и паллетные перемещения — проверяемый сквозной пример. Для аэропорта и
клиники интерфейс должен честно показывать, какие шаги реально поддерживаются;
не обещать одинаково полный результат без отдельной проверки. В ТЗ требуется
доступный демонстрационный набор, сравнение baseline с двумя вариантами
роботизации, чувствительность, 2D и связанные KPI. Дополнение фиксирует для
baseline финансирование собственными средствами и допускает обоснованные,
явно обозначенные допущения. Результат остаётся предварительным при C05
`NEEDS_VALIDATION` и закупке `UNVERIFIED`.

## Порядок работ в новой сессии

Каждый этап заканчивать отдельным коммитом и проверкой именно затронутого
поведения. При изменении контракта создать новую версию; сохранённые
`analysis_runs`, `simulation_artifacts` и их SHA-256 не изменять. Полный
регрессионный прогон и production-приёмка — в последнем этапе.

### 1. Читаемые числа и честные отчёты по типу результата

Сделать единый форматтер экранных и PDF-показателей: максимум два знака после
запятой, русские разделители и единицы, парк целым числом, доли покрытия и
загрузки процентами (`0.990675…` → `99,07 %`, `1` → `100 %`). Для долей рядом
дать понятное определение и не смешивать загрузку с количеством роботов.
Форматировать **только представление**: Decimal в API, формулах, snapshots,
машинном ZIP и проверочных digest сохранять без округления.

Разделить PDF/ZIP и заголовки результатов по типам: C11 — техническая
мощность, допущения/ограничения и следующие необходимые данные; частичный
economics — рассчитанные ветки, точные причины пробелов и следующий шаг;
полный economics — сравнение baseline/покупки/RaaS. Вернуть экспорт частичному
run и сделать очевидной связь economics run с исходным C11. Разделы без
рассчитанных денег не растягивать на страницы с повтором «нет данных».
Проверить старый C16 v1 с предупреждением и неизменные значения в старых
снимках.

**Готово:** приведённые пользователем величины выглядят как `15 роботов`,
`196,64 ед./ч`, `137,65 ед./ч`, `100 %`, `99,07 %`; три вида PDF соответствуют
типу run, русский текст ищется, числовая сумма совпадает с сохранённым
результатом до округления; частичный run даёт скачать PDF/ZIP.

### 2. Версионированный демонстрационный сценарий и ввод своих данных

Добавить отдельные **демо-наборы допущений для сценария** для проверяемого
складского процесса. Взять числовые примеры из рабочих тестовых сценариев
только после проверки смысла, единиц, диапазонов и взаимной согласованности;
не называть их фактическими ценами или нормами организатора. Развести в UI:
официальный параметр объекта, пользовательское значение, предлагаемое
сценарное допущение и неподтверждённое коммерческое условие. Каждое
предложенное число имеет версию, источник/обоснование, дату и возможность
изменить или очистить. Выбор «Допущение для сценария» при наличии шаблона
заполняет поле предлагаемым числом, явно показывает его происхождение и
требует подтверждения; при отсутствии шаблона объясняет, что нужно ввести
число вручную. Выбор «Данные пользователя» никогда не стирает введённое.

Сделать два видимых входа: гостевое демо без сохранения чувствительных данных
и проект с ручным/файловым вводом. Показывать минимальный набор полей для C11,
труда, покупки, RaaS и визуализации отдельно, с индикатором полноты каждой
ветки. Сохранять выбранные источники в новых versioned snapshots. Значение 0,
пустое значение и диапазон сохраняют разную семантику. C05 и procurement не
становятся положительными от выбора допущения.

**Готово:** из демо склада за несколько минут получается полный проверяемый
сценарий с baseline, покупкой, RaaS и чувствительностью при явно
подтверждённых предпосылках; собственный неполный ввод по-прежнему даёт
частичный результат без вымышленной суммы. После изменения одного допущения
создаётся новый run, старый воспроизводится.

### 3. Визуализация для технического и частичного расчёта

Отвязать подготовку **технического ScenarioSpec** от готовности финансовых
веток. Определить минимальные входы C23: нагрузка/парк, режим работы,
задачи/маршруты, время начала и часовой пояс либо явно согласованный
условный календарь. Недостающее спрашивать до запуска или показывать точный
список причин; не подставлять молча данные тестов. Новые расчёты сохраняют
валидный versioned ScenarioSpec при достаточных технических входах и
показывают 2D/C23 на экране C11 и частичного результата. В интерфейсе явно
различать «схема работы доступна» и «денежный эффект не рассчитан».

Для уже сохранённых C11/partial run без валидного ScenarioSpec не менять
snapshot: создать новый связанный immutable технический run/артефакт с
проверенной привязкой к исходному C11 либо предложить новый расчёт с
предзаполненным подтверждаемым вводом. Выбранный вариант зафиксировать в
контракте и тестах. KPI берутся из C23, геометрия без плана помечена
условной; 2D/3D не выдаются за телеметрию объекта.

**Готово:** новый частичный run только с достаточными техническими данными
даёт запуск, сохранение и повторное открытие 2D/C23, при этом NPV остаётся
«не рассчитано». Старый `78b71ff3…` и его дочерние runs неизменны; экран
объясняет, как построить визуализацию для их данных.

### 4. Один расчётный маршрут v2 и зоны как часть процесса

Убрать legacy переключатели «Весь объект» и «По зонам» из пути **нового**
расчёта и всех входных CTA. Стартовать с процесса и роли; объект остаётся
контекстом. Старые URL/API и replay сохранённых v1 runs оставить доступными
для чтения и совместимости, без создания нового legacy run из обычного UI.
Проектировать v2 как `объект → зона → процесс/роль`: одна зона по умолчанию,
при добавлении зоны — её нагрузка, маршрут и ограничения; общие затраты
площадки вводятся один раз. В C11 считать мощности по процессам/зонам и
агрегировать парк только там, где это математически корректно; общие роботы,
межзональные потоки и разделяемые ресурсы обозначить явно и не суммировать
двойным счётом. 2D использует те же идентификаторы зон и задач. Если полный
многозонный расчёт не готов к защите, сохранить один честный складской
golden path и ясное ограничение для остальных конфигураций.

**Готово:** новый пользователь видит один путь расчёта, может добавить зону
в v2 и понимает, как она влияет на входы и результат; старый v1 run
открывается и экспортируется с прежними числами.

### 5. Помощник как проводник по сервису

На странице «Процесс» дать 5–8 стартовых вопросов: что умеет сервис,
какие данные нужны, можно ли считать без цены, чем допущение отличается от
факта, почему нет NPV, где 2D, как читать C05/закупку, как сравнить роботов.
Добавить короткое интервью: процесс → груз/операция → объём и пики → режим
→ расстояние/зоны и ограничения → данные о персонале/экономике. На каждом
шаге показывать, что уже известно, что ещё нужно для конкретной ветки и
почему. Сохранить черновик профиля в проекте для вошедшего пользователя;
гостю — в сессии с понятным сроком жизни. По подтверждению пользователя
переносить числа и источники в v2 форму; помощник не запускает расчёт
неподтверждёнными значениями.

Существующее сравнение 2–3 позиций расширить нормализованными критериями,
пропусками и ссылками на источник; не превращать совпадение слов в вердикт
пригодности. Проверить поиск на небольшом наборе реальных вопросов и
неподходящих ответов. Если лексический поиск заметно промахивается,
прототипировать гибридный/векторный retrieval с оценкой качества, версией
активного каталога и стоимостью; эмбеддинги сами по себе не являются
критерием готовности. Внешний поиск остаётся отдельным и не меняет каталог.

**Готово:** новый посетитель проходит интервью до подтверждённого черновика,
возвращается к нему, импортирует данные в расчёт и получает объяснение
частичного результата; тесты покрывают чужой проект, спорный факт и
недоступность внешнего поиска.

### 6. Лендинг и короткий путь к ценности

Сделать первый экран продуктовым лендингом с ясным обещанием:
«От процесса до предварительного сценария роботизации»; тремя конкретными
выходами — подбор с источниками, мощность/экономика с допущениями, 2D-схема
с KPI. Показать «как работает» в 3–4 шага, пример результата склада,
ограничения предварительной оценки и CTA «Попробовать демо» / «Рассчитать
свой процесс». Добавить понятный переход к каталогу и FAQ. Не заявлять
«окупаемость гарантирована», «подходит для закупки» или «цифровой двойник».
Согласовать визуальный язык лендинга с приложением; проверить 1366×768,
мобильную ширину, клавиатуру и читаемость русского текста.

**Готово:** человек без инструктора за один экран понимает, для кого сервис,
что он получит и куда нажать; обе CTA ведут в работающие маршруты, а не в
legacy форму или экран входа без объяснения.

### 7. Сквозная приёмка и выпуск

На одноразовой локальной БД пройти миграции и профильные backend/frontend/
RobCraft проверки, затем в настоящем браузере — гостевое демо и проект со
своими данными, полный и частичный результат, 2D, сравнение, сохранение,
reopen/replay, PDF/ZIP. Проверить 1366×768 и узкий экран, точность PDF
относительно immutable run, источники допущений, изоляцию арендаторов,
CSRF, старый C16 v1, integrity C23 и каталог/медиа. Зафиксировать короткий
сценарий показа и ограничения. После проверенного `main` выполнить обычный
fast-forward выпуск и HTTPS-приёмку того же пути; команды для сервера дать
простыми строками для Windows CMD. Серверных бекапов не требовать.

**Готово:** комиссия может пройти маршрут без ручного объяснения интерфейса;
demo-run воспроизводим, неполный ввод остаётся честным, старые runs не
изменились, production HEAD/Compose/`/ready` и реальный пользовательский
путь зафиксированы отдельно. При недостатке времени приоритет — сквозной
складской маршрут, затем остальные типы объектов и улучшение retrieval.
