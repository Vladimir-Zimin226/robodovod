# Экономика и зональный расчёт Robomera 3.4

Актуально на 15 сентября 2026 года. Этот документ фиксирует результат интеграции
версии `robomera`, полученной из `Разобрать/projects`, в основной репозиторий и
последующие исправления этапа A интеграции RobCraft.

## Что реализовано

Backend поддерживает два режима `POST /api/calculate`:

- `whole` — единый процесс на всём объекте;
- `zonal` — набор независимых зон с собственными процессом, объёмом, графиком,
  штатом, требованиями к грузу и необязательным ручным размером парка.

Зона преобразуется в обычный расчётный вход, после чего для неё выполняются те же
hard constraints, sizing и экономические сценарии. Итоги зон агрегируются в общую
сводку. Объектовый fixed CAPEX берётся один раз, а зональный fixed CAPEX — для
каждой зоны.

Frontend позволяет переключаться между единым и зональным режимами, добавлять и
настраивать зоны, видеть сводку и результаты каждой зоны, выполнять what-if по
зарплате, горизонту, ставке, объёму, сменам, штату, высвобождению и размеру парка,
а также формировать отдельный зональный PDF.

Вход `UserInput` и вложенные `Zone` строгие: неизвестные поля дают validation
error, `zone.id` должны быть уникальны, а `units_per_trip` принимается и имеет
приоритет над значением из каталожного `transport_profile`. Frontend перед
отправкой исключает только свои служебные поля с префиксом `_`; они не являются
частью API. Каждый успешный ответ имеет `schema_version=calculation-response-v1`,
общий `revision_id` и вложенный `scenario_spec`. Zonal-ветка используется и при
автоматическом завершении интервью, а не только при ручной кнопке расчёта.

## Расчётная модель

Для каждого допустимого решения считаются пессимистичный, базовый и
оптимистичный сценарии. В расчёте участвуют:

- размер парка по пропускной способности и пиковой доле смены;
- пользовательская вместимость рейса `units_per_trip`;
- роботы, зарядки, интеграция, fixed CAPEX и contingency;
- сервис, ПО, электричество и замена батарей;
- полная стоимость FTE: месячный оклад × 12 × 1,55;
- штат, который технически можно заменить, выбранное пользователем
  высвобождение и минимальный персонал на пульте по сменам;
- инфляция труда 8% и OPEX 5%;
- остаточная стоимость оборудования;
- дисконтированные денежные потоки, NPV, TCO, ROI и окупаемость;
- горизонт проекта от 5 до 10 лет.

Поле каталога `economics.fte_replace_per_shift` используется как верхняя граница
заменяемого труда: `robots × shifts × fte_replace_per_shift × rotation_factor`.
Итог дополнительно ограничен покрываемым спросом и фактическим штатом. Это явное
решение этапа A; поле больше не является мёртвыми данными.

Рекомендации имеют `technical_status`, `economic_status` и `is_best`.
Принудительно показанный несовместимый вариант получает `FORCED_UNSUPPORTED`.
Вариант с неположительным годовым эффектом либо одновременно неокупаемый в
горизонте и с отрицательным NPV получает `NOT_ACCEPTABLE`: он остаётся в
сравнении с предупреждением, но не получает `is_best`. Отрицательный NPV или
неокупаемость по отдельности дают `WARNING`.

Зона получает один из статусов `RECOMMENDED`, `NO_ELIGIBLE_EQUIPMENT` или
`NO_ACCEPTABLE_ECONOMICS`; два последних сопровождаются `status_message` и не
создают ложную рекомендацию в `ScenarioSpec`.

Для интегрированного 3D зона `NO_ACCEPTABLE_ECONOMICS` может содержать одну пару
`fleet`/`task_profile` технически допустимого варианта. Это только visualization
candidate: статус зоны остаётся отрицательным, `is_best` отсутствует, а допущение
`VISUALIZATION_ONLY_NOT_RECOMMENDATION` и UI явно сообщают, что вариант не
рекомендован. `NO_ELIGIBLE_EQUIPMENT` по-прежнему всегда имеет пустой парк.

Frontend-дефект исправлен 15 сентября 2026 года. Dashboard, каталог результата,
комбинированные сводки и whole-PDF определяют рекомендацию только по `is_best`.
При `NO_ACCEPTABLE_ECONOMICS` интерфейс показывает спокойное объяснение, не
назначает звезду, не подставляет первый вариант в KPI и не формирует PDF с ложной
рекомендацией. Структура ScenarioSpec не менялась; уточнена семантика существующих
`fleet`/`task_profiles` для отрицательного статуса зоны.

Результатный frontend теперь использует отдельный presentation-adapter и тёмный
visualization-first dashboard для whole- и zonal-режимов. Все финансовые KPI
берутся из ответа backend. Поскольку контракт не содержит cash-flow series по
годам, интерфейс показывает NPV, TCO и годовой чистый эффект без самостоятельного
воспроизведения дисконтированной модели.

## ScenarioSpec v1

Канонический межъязыковой контракт находится в
`contracts/scenario-spec-v1.schema.json`. Backend формирует его целиком; frontend
и будущий адаптер RobCraft не должны выводить экономику из внутренних объектов.

- `schema_version` — строго `scenario-spec-v1`;
- `revision_id` — детерминированный `calc_<16 hex>`, общий с расчётным ответом;
- `template` и `seed` задают воспроизводимую концептуальную сцену;
- `facility` содержит геометрию или явные `null` и `geometry_status`;
- `zones` содержат процесс, спрос и статус каждой зоны;
- `fleet` содержит точную модель, количество, скорость и payload назначенной
  рекомендации либо явно маркированного visualization candidate;
- `task_profiles` фиксируют спрос, `units_per_trip` и время обмена;
- `economics` — неизменяемый backend snapshot со статусом;
- `assumptions` и `warnings` объясняют границы результата.

Неизвестная major-версия и неизвестные поля отклоняются Python DTO и JavaScript
contract-тестом. `null` означает неизвестное значение и не заменяется нулём.

Ручное уменьшение парка снижает покрытие процесса и экономический эффект, а не
сохраняет эффект полного парка. Ограничения проверяют назначение класса робота,
тип груза, грузоподъёмность, ширину прохода и достижимость рейса по автономности.

## Каталог

Монолитный `backend/robots.json` заменён каталогом `backend/fleet/*.json`, который
валидируется Pydantic-моделями при старте. Сейчас загружаются 13 решений в пяти
категориях: внутренний транспорт, сервисная доставка, уборка, стационарная
паллетизация и воздушные платформы. Для frontend добавлены endpoints категорий и
карточки отдельного робота.

## Что зональный режим пока не делает

- Зоны экономически независимы: общие ограничения ресурсов, очереди и передача
  роботов между зонами не моделируются.
- Нарисованные в 2D зоны — условная раскладка по площади, а не исходные полигоны
  плана объекта.
- Агрегированная сводка строится по лучшей рекомендации каждой зоны; переключатель
  сценария меняет детализацию сценариев, но не пересчитывает агрегат отдельным
  backend-сценарием.
- RobCraft этапа G принимает многозонный ScenarioSpec и строит отдельные
  репрезентативные сцены транспорта, клинической доставки, уборки и паллетизации.
  Единая физическая модель здания с общими коридорами и межзональными конфликтами
  пока не реализована; переданный polygon служит справочным overlay.
- Каталожные цены и нормативы являются плановыми допущениями и требуют проверки
  источников перед использованием вне демонстрационного ТЭО.
- PDF загружает кириллический шрифт с CDN, поэтому именно экспорт PDF требует
  доступа в интернет; расчёты и интерфейс работают локально.

## Запуск и проверка

Основная Docker-инфраструктура сохранена. Frontend использует относительный
`/api`, который Vite проксирует на локальный backend, а Nginx — на сервис
`backend` внутри Compose.

```powershell
docker compose up --build
```

При реализации были выполнены проверки исходников:

```powershell
Push-Location backend
..\.venv\Scripts\python.exe -m pytest -q
Pop-Location
npm.cmd run lint --prefix frontend
npm.cmd run build --prefix frontend
docker compose config --quiet
```

Результат актуальной локальной проверки после redesign: 175 backend-тестов,
75 тестов RobCraft, 3 ScenarioSpec contract-теста и 8 frontend-тестов пройдены;
ESLint не сообщает ошибок, production bundle и frontend Docker image собираются,
Compose-файл валиден. Дополнительно реальный локальный Uvicorn вернул HTTP 200 для корневого
endpoint, каталога, категорий, whole-расчёта и zonal-расчёта. После smoke-проверки
процесс Uvicorn был остановлен.

Отдельный runtime-smoke Docker Compose 15 сентября 2026 года подтвердил состояние
`healthy` у backend и frontend, проксирование `/api/calculate` и `/api/robots`, а
также HTTP 200 для embedded `/robcraft/?embedded=1` и его ES-модулей. Frontend
build context расположен в корне репозитория; в `frontend/Dockerfile` путь к
Nginx-конфигурации должен оставаться `frontend/nginx.conf`.

Golden экономика этапа A зафиксирована в
`backend/fixtures/economics-warehouse-v1.json`. Файл объявлен неизменяемым: при
сознательном изменении модели создаётся новая версия fixture, существующие
ожидания не переписываются. Межъязыковой fixture находится в
`contracts/fixtures/scenario-spec-v1.golden.json`.

### Совместимость и миграция этапа A

Endpoint `POST /api/calculate`, прежние входные имена и прежние поля ответа
сохранены. Изменения для клиентов:

1. удалить опечатки и произвольные поля из payload — они теперь дают HTTP 422;
2. служебные UI-поля с `_` хранить локально, не отправлять в API;
3. обеспечить уникальность `zone.id`;
4. читать `is_best`, а не считать первый элемент безусловно лучшим;
5. обрабатывать статусы зон и предупреждения верхнего уровня;
6. использовать `revision_id` ответа и `scenario_spec.revision_id` как одну
   атомарную ревизию.
