# Состояние для следующей сессии · 17.10.2026

## Где остановились

Последняя задача пользователя — замечание Евгения «сервис просчитывает только одну роль». В проекте уже есть пакетный расчёт отдельных **операций** по зонам, но денежный трудовой эффект одной операции строится для одной явно выбранной роли. Это ограничение формулы C14 и входного контракта, а не отсутствие ролей в форме. У складского `warehouse_receiving_shipping` могут быть водитель погрузчика и грузчик; у каждого свой труд, но один физический поток и один парк. Копировать процент покрытия робота на обоих означало бы без доказательства удвоить экономию.

## Что сделано в последнем изменении

- `frontend/src/economicsInputV2.js` больше не выбирает первую из нескольких ролей по порядку чекбоксов. При отсутствии выбора сервер сохраняет частичный результат. В форме `EconomicsInputsV2.jsx` явно спрашивается, чью работу заменяет операция; оценка ручной выработки применяется только после выбора роли.
- `frontend/src/components/ProcessRoleIntakeV2.jsx` ведёт через расчёт всех выбранных операций, открытие каждой операции для экономики и объединение рассчитанных веток покупки. Сводка показывает роли и статусы трудового эффекта.
- `backend/project_portfolio.py` формирует `role_effects` и `unassessed_roles`: `CALCULATED`, `PARTIAL`, `NOT_CALCULATED`, связанные и непокрытые операции, число высвобождённых людей только для рассчитанной части. Роли заблокированных операций сохраняются в итоговой сводке.
- `backend/persistence_api.py` сохраняет `role_refs` в пакете, сверяет их с сохранённым расчётом мощности, помечает проектный итог частичным при непокрытых ролях и выводит охват в PDF. Новая схема проектного отчёта — `project-portfolio-economics-v2`; прежние сохранённые снимки не переписываются.

Последний подтверждённый пользователем деплой — `02949bb`: приложение и публичная smoke-проверка работали. Изменение выше проверено локально; деплой этого изменения в рамках данной сессии не выполнялся. Сверяйте текущий `git log` и состояние сервера, прежде чем считать его опубликованным.

## Что ещё нужно для настоящего расчёта нескольких ролей в одной операции

1. Вместе с Евгением описать работу каждой роли внутри процесса: объём её задач, ручную выработку, долю задач, которые выполняет конкретная модель робота, и остаточные ручные действия. Уточнить, какие роли выполняют один и тот же этап, а какие — разные этапы одного потока.
2. Версионировать вход и C14 так, чтобы одна физическая операция и один парк связывались с несколькими **отдельными** трудовыми задачами. Расходы на парк, управление и техподдержку должны учитываться один раз; зарплата, исходный штат, остаточная работа и высвобождение — по каждой роли. Не создавать второй физический парк для второй роли.
3. Проверить расчёт на примере «водитель погрузчика + грузчик» с нулевым/частичным/полным покрытием каждой задачи, разной выработкой и зарплатой. Добавить контрактные и интеграционные тесты C14/C18 и UI; сравнить сохранённые PDF/ZIP с источниками.
4. Для профилей без утверждённой физической формулы (например, полный отбор/комплектация) сохранять `NOT_CALCULATED` до появления модели производительности и данных каталога. Не превращать исследовательское упоминание робота в денежную экономию.
