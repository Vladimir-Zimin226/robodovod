# Администратор: каталог, источники и нормы — F3

Путь: учётная запись ADMIN → **«Каталог и источники»**, либо `#admin-catalog`.
Базовые операции выполняются в браузере. Опубликованные версии доступны для
просмотра; правки сохраняются в собственной новой версии.

## Ручное управление по 3.3.5

1. Выберите опубликованную версию, задайте уникальный код, например
   `catalog-2026-09-26-01`, нажмите **«Создать черновик»**.
2. **«Источники»**: добавьте HTTP(S) URL или название/ссылку документа, фактические
   даты получения и обновления, комментарий. URL не загружается сервером.
   `inherited:` ссылается на immutable evidence родителя; неизвестные даты
   остаются пустыми, исходная provenance остаётся в родительском каталоге.
3. **«Решения и ТТХ»**: добавьте название, производителя, семейство, тип,
   назначение, страну, доступность, инфраструктуру, срок службы. Для каждой ТТХ
   укажите код, scope, каноническую unit, тип значения, source/status/comment.
   Пустое значение — unknown. Для нового кода сначала добавьте справочник
   `spec` с unit и source. NUMBER требует конечного неотрицательного числа,
   BOOLEAN — `true`/`false`, JSON — валидного JSON списка/объекта.
4. **«Предложения»**: создайте отдельные позиции одной модели с собственными
   ключами и ценами. Укажите применимость, регион, способ приобретения,
   валюту ISO, статус и ставку НДС (доля 0–1), период цены, включённые и
   исключённые услуги, источник и комментарий проверки. Дубли предложений
   одной модели не схлопываются. Пустая цена не равна нулю.
5. **«Нормы»**: задайте допустимое сценарное предложение с units, источником,
   границами и основанием. **«Справочники»** позволяют добавить тип,
   доступность, отрасль или код ТТХ с источником. Формулы/registry не меняются.
6. **«Сохранить и показать diff»** → раскройте before/after → **«Проверить
   версию»** → подтвердите проверку → **«Опубликовать версию»**. Публикация
   ещё не переключает активный каталог. После новой правки требуется новая
   валидация, даже если статус уже VALIDATED.
7. По умолчанию активируется discovery. Для новых C11 выберите **«Переключить
   discovery и capacity вместе»** и подтвердите действие. Legacy runtime
   можно добавить только при наличии evidence-backed legacy позиций; иначе
   это явно показано. Выбранные указатели переключаются одной транзакцией.
8. Для возврата выберите прежнюю опубликованную версию, указатели, подтвердите
   действие и нажмите **«Активировать выбранную версию / вернуть указатель»**.
   **«Показать аудит»** показывает администратора, время и изменения.

Draft mutation/publish разрешены владельцу. Другие ADMIN могут просмотреть
версию или создать собственный черновик от published. При конфликте редакции
или активного указателя сервер возвращает 409; загрузите данные заново.

## Публикация и расчётная готовность

Статус версии, полнота ТТХ, readiness моделей и разрешение capacity activation
показаны отдельно. Публикация информационных решений допустима. Импортируемое
поле `calculation_ready` запрещено. Checkbox принудительного разрешения нет.

Новая модель, новое предложение или изменённый физический профиль остаются
информационными с объяснением необходимости evidence и rollout. Подтверждение
характеристики не выдаёт новое разрешение rollout. Совместимый неизменённый
утверждённый профиль сохраняет факты и evidence IDs, проходит прежние C05/C06
gates. Сервер сравнивает исполняемый пул новой версии с исходным каталогом,
который проверяется принятой `capacity-runtime-rollout-policy-v1`: membership,
факты, scopes/units, assumptions, профили и runtime version должны совпасть.
Расширение физического пула требует отдельного принятого rollout. Карточки,
цены, справочники и нормы не переписывают утверждённые физические факты.
Пригодность для объекта и deployment readiness сохраняют существующие gates.

## Нормы и новые расчёты

| Поле | Единица | Допустимые границы |
|---|---|---|
| `exchange_seconds` | `s` | 0.001–86400 |
| `units_per_trip` | `pallet/trip` | целое 1–100000 |
| `operating_days` | `day/year` | целое 1–366 |

Требуется `minimum ≤ lower ≤ value ≤ upper ≤ maximum`, source и comment.
В «Моделировании процесса» пользователь нажимает **«Предложить …»**.
Создаётся новая версия профиля с неподтверждённым `expert_assumption`, source
и catalog binding. Затем пользователь отдельно подтверждает профиль и
запускает новый расчёт. Подтверждённое значение нельзя заменить нормой.
Старые профили/runs/артефакты сохраняют старые числа; автоматической подстановки
vendor facts и редактирования registry constants нет.

## «Обновить каталог»: поддержанный файл

UTF-8 JSON `admin-catalog-v1`, максимум 4 МиБ. Задайте новый код версии,
нажмите **«Скачать JSON для обновления»**, затем загрузите через **«Обновить
каталог · JSON»**. Оболочка содержит `code`, `parent_code`, `document`.
Документ содержит `schema_version`, `base_catalog_code`, `base_content_sha256`,
полные списки `models`, `offers`, `sources`, `defaults`, `dictionaries`.
Сохраните исходные SHA и стабильные ключи из экспорта; исходные модели и
предложения нельзя удалить. Новые записи получают новые ключи.

Проверяются обязательные/лишние поля, references, units/types/ranges,
dates/currency/VAT и дубли ключей. Формулы, макросы, ZIP extraction и shell
не выполняются. После проверки создаётся staged draft/diff; validate,
publish и activate — отдельные действия. Повтор того же документа с тем же
кодом владельцем возвращает существующую версию без дублей. Другой документ
с занятым кодом получает 409.

## API

Все `/api/admin/catalog` требуют ADMIN session cookie. Мутации требуют
совпадающий `X-CSRF-Token`; draft mutation/publish дополнительно owner.

| Метод и путь относительно `/api/admin/catalog` | Назначение |
|---|---|
| `GET /` | Версии и активные указатели |
| `GET /versions/{code}` | Document/revision/diff/readiness/completeness |
| `POST /versions` | `{code, parent_code}` → собственный draft |
| `PUT /versions/{code}` | `{expected_revision, document}` → атомарная правка |
| `GET /versions/{code}/sections/{section}` | models/offers/sources/defaults/dictionaries |
| `PUT /versions/{code}/sections/{section}` | `{expected_revision, entries}`, полная валидация документа |
| `POST /import` | Оболочка JSON → staged draft / idempotent result |
| `POST /versions/{code}/validate` | `{expected_revision}` → digest редакции |
| `POST /versions/{code}/publish` | `{expected_revision}` → публикация проверенной редакции |
| `POST /versions/{code}/activate` | `{slots, expected_active}` → atomic switch / rollback |
| `GET /audit` | Последние 200 actor/time/change событий |

`slots`: уникальный непустой список `discovery`, `capacity`, `runtime`.
`expected_active`: код или `null` для каждого выбранного указателя.
Published документы защищены PostgreSQL trigger. Миграция `0012_admin_catalog`
добавляет таблицу, не обновляет existing organizer rows/runs. Downgrade
запрещён при наличии опубликованной административной истории.

`GET /api/catalog/defaults` публично показывает предложения активного discovery.
Owner/CSRF `POST /api/brain/projects/{id}/catalog-default` принимает
`{expected_version, catalog_code, field}` и создаёт только новую версию профиля.

## Браузерная проверка

[browser_f3_acceptance.py](../scripts/browser_f3_acceptance.py): ADMIN → ручное
решение и две цены → source/default/dictionary → diff → validate → publish →
activate → JSON download/upload/repeat → manual edit → publish → activate →
UI rollback → норма → confirm → C11. Проверяются desktop/mobile, 220/120,
типовой склад, старые PDF/XLSX и полные historical rows до/после.
